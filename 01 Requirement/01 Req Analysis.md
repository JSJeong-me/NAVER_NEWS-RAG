## 3. 기능 요구사항 – 뉴스 분석·종목 매핑

### 3.1 뉴스 → 종목 매핑

1. **종목 사전 관리**

   * 국내 상장사(코스피/코스닥) 기준:

     * `종목코드`, `종목명`, `영문명`, `주요 약어/별칭` 정보.
   * 사전은 **정기적으로 업데이트** 가능한 구조.

2. **매핑 로직**

   * 기사 **제목 + 본문**에서:

     * 종목명, 티커, 기업명 키워드 탐지.
   * 단일 기사에 **복수 종목**이 포함될 수 있음.
   * 종목 매핑 결과:

     * `news_id`, `symbol`, `match_score` (정확도 점수) 형태로 저장.

3. **뉴스 분류**

   * 최소한의 카테고리:

     * **시장 전체(Macro / Index)** 뉴스
     * **섹터/산업** 뉴스
     * **개별 종목** 뉴스
   * 카테고리 분류는:

     * 룰 기반(키워드) + 추후 ML/LLM 도입 여지를 남김.

### 3.2 텍스트 분석 및 스코어링

1. **Sentiment 분석**

   * 기사별 **Sentiment Score** 산출:

     * 예: [-1.0, 1.0] 구간의 연속값 또는 {매우부정, 부정, 중립, 긍정, 매우긍정}.
   * 기사 수준, 종목 수준 둘 다 제공:

     * `article_sentiment`
     * `symbol_sentiment` (기사 내 해당 종목에 대한 평균 or 가중 평균).

2. **리스크 태깅**

   * 다음과 같은 리스크 키워드/토픽을 탐지:

     * 규제/정부 정책, 수사/제재, 실적부진, 구조조정, 리콜, 파산·법정관리, 지정감사, 회계이슈 등.
   * 각 뉴스에 **Boolean 또는 Score** 형태로 태깅:

     * `regulatory_risk_flag`, `earnings_risk_flag`, `credit_risk_flag` 등.

3. **중요도(Impact) 스코어**

   * 뉴스가 **가격에 미칠 잠재적 영향도**를 점수화:

     * 언론사 신뢰도
     * 제목/본문 내 강한 표현(“급락”, “충격”, “사상 최고” 등)
     * 시장/섹터/종목 범위(전시장 vs 개별 종목)
   * `impact_score` (예: 0~1 또는 0~100) 산출.

4. **시간 정보 정규화**

   * 네이버 표기 시각을 **표준 시각(Asia/Seoul)** 기준 `published_at`으로 저장.
   * 크롤링 시간 `crawled_at` 과 분리 저장.

### 4.1 입력·출력 요구사항

1. **입력**

   * 종목별:

     * `symbol_sentiment`
     * `impact_score`

2. **출력**

   * 매수 후보 리스트:

     * 각 종목별:

       * `symbol`
       * `reason_summary` (간단 요약 문장)
       * `sentiment_score`
       * `impact_score`
       * `risk_flags`
       * `conf_level` (추천 신뢰도).
   * 상위 N개 종목 (예: Top 10) 제공.

### 4.2 추천 로직 요구

1. **룰 기반 최소 조건**

   * 긍정적 뉴스 중심:

   * 심각한 리스크 플래그가 **False**일 것.

2. **중복 & 변동 관리**

   * 같은 종목이 이미 매수 후보로 추천된 상태에서 새로운 뉴스가 나왔을 때:

     * 신뢰도 증강/감소, 후보에서 제외 여부 결정.
   * 추천 이력 관리:

     * `recommendation_id`, `created_at`, `status(유지/철회)`.

3. **전략 연동**

   * 향후:

     * LLM 기반 “뉴스 요약 + 투자의견” 생성 모듈과 연동 가능해야 함.
     * 기존 **Analyst Agent / Trader Agent** 의 입력 피처로 사용될 수 있도록 **JSON 구조 표준화**.

## 5. 기능 요구사항 – 시장 Regime 판단 엔진

### 5.1 Regime 정의

1. 최소 Regime 예시 (추후 확장 가능)

   * **Bullish**: 긍정 뉴스가 다수, 리스크 낮음.
   * **Bearish**: 부정 뉴스 비중↑, 리스크 플래그↑.
   * **High Volatility / Event-Driven**: 긍·부정 모두 강하고 impact_score 높은 뉴스가 다수.
   * **Risk-off**: 규제, 거시 리스크, 지정학적 이슈 등 부정적 macro 뉴스 집중.
   * **Neutral / Sideways**: 뚜렷한 편향 없음.

### 5.2 판단 로직

1. **집계 단위**

   * 최근 **N시간 (예: 6시간, 24시간)** 기준 전체 뉴스에 대해:

     * 평균 Sentiment
     * 부정/긍정 기사 비율
     * 주요 리스크 플래그 발생 비율
     * macro/섹터/종목 뉴스 비중.

2. **판단 방식**

   * 초기에는 **룰 기반**:

     * 예: 최근 24시간 avg_sentiment > 0.3 & reg_risk 비율 < 5% → Bullish.
   * 향후:

     * ML/통계 모델(클러스터링, HMM, 마르코프 Regime switching 등)로 대체 가능하도록 설계.

3. **출력 형식**

   * `current_regime` (라벨)
   * `regime_confidence` (0~1)
   * `explanation` (간단 요약 문장: “규제 뉴스 급증으로 위험회피 국면” 등).

## 6. 데이터 저장 & 3일 보존/아카이빙 요구사항

### 6.1 DB 저장 요구사항

1. **저장 대상**

   * 뉴스 원문 및 메타:

     * `news` 테이블: id, title, body, url, publisher, category, published_at, crawled_at, created_at, updated_at 등.
   * 종목 매핑:

     * `news_symbol_map`: news_id, symbol, match_score.
   * 분석 결과:

     * `news_analysis`: news_id, article_sentiment, risk_flags, impact_score 등.
   * 추천/Regime:

     * `recommendations`: recommendation_id, symbol, created_at, status, scores, explanation 등.
     * `regime_history`: timestamp, regime_label, confidence, explanation.

2. **조회 성능**

   * 최근 24~72시간 데이터를 **빠르게 조회**할 수 있도록:

     * `published_at`, `symbol` 기준 인덱스.
   * 3일 데이터만 DB에 남기므로, 테이블 크기는 상대적으로 작게 유지.

### 6.2 3일 보존 정책 & 아카이빙

1. **보존 정책**

   * DB에는 **최근 3일(72시간)** 의 데이터만 유지.
   * 3일이 지난 데이터는:

     * **파일로 저장 후** DB에서 삭제.

2. **아카이빙 방식**

   * 파일 포맷:

     * 재활용·분석 용이성을 위해 **JSONL 또는 Parquet** 권장.
   * 파일 단위:

     * 날짜별, 또는 하루 단위/시간 단위 등:

       * 예: `news_2025-12-02.parquet`, `analysis_2025-12-02.jsonl`.
   * 포함 내용:

     * news, news_symbol_map, news_analysis, recommendations, regime_history 를 **동일 날짜 범위 기준**으로 분리.

3. **아카이빙 프로세스**

   * 별도의 **일일 배치(Job)**:

     * 예: 매일 새벽 02:00에:

       * `published_at < (오늘 - 3일)` 인 데이터 조회.
       * 파일로 덤프.
       * 성공 시 해당 레코드 DB에서 삭제.
   * 실패 시:

     * 재시도/오류 알림.
