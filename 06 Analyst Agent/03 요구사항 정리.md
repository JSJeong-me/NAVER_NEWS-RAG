위 분석 내용을 수행하는 'Analyst Agent'는 '/home/ubuntu/news_regime' directory 내에서 제공하는 cli 를 실재 30분(Configurable) 단위로 실행하고 얻은 정보를 분석하여 report 가 목적입니다. 다음단계인 '프로그램 설계'를 위한 '요구사항 분석'을 정리해 주세요.



Analyst Agent는 이제 **“/home/ubuntu/news_regime 안에 이미 있는 CLI들을 30분마다 자동으로 돌리고, 그 결과를 해석해서 리포트로 정리하는 자동 애널리스트”** 입니다.
다음 단계(프로그램 설계)를 위해, 이 Agent 자체에 대한 **요구사항 분석**을 정리해 볼게요.

---

## 1. 목적 & 범위

### 1.1 목적

* Naver 금융 주요 뉴스 기반으로 구축된 기존 파이프라인 결과(뉴스/분석/추천/Regime)를,

  * **30분(설정 가능) 주기**로 수집·해석하여
  * **시장 Regime 변화**와 **급격한 변동성 신호**를 빠르게 감지하고
  * 사람이 바로 읽을 수 있는 **분석 리포트**로 제공하는 것.
* Analyst Agent는 **데이터를 직접 크롤링/분석하는 주체가 아니라**,
  `/home/ubuntu/news_regime` 내 **기존 CLI를 “툴”로 호출해서** 결과를 소비하는 상위 애널리스트 레이어.

### 1.2 범위

* **범위 포함**

  * CLI 실행 스케줄 관리(30분 주기, configurable)
  * `query_db.sh` / 필요 시 `run_crawler.sh`, `list_news.sh` 실행 및 결과 파싱
  * Regime/변동성/추천 종목 등에 대한 자동 분석 로직
  * 분석 결과를 리포트 포맷으로 생성 및 저장/출력
* **범위 제외**

  * Naver 뉴스 크롤러, 분석 엔진, DB 스키마 변경 (이미 구현된 것으로 가정)
  * 실제 주문/트레이딩 실행
  * 실시간(초 단위) 알파 전략 — 이 Agent는 “30분 단위 요약/브리핑” 역할

## 2. 운영 환경 & 외부 인터페이스

### 2.1 운영 환경

* Host : `nvidia jetson agx orin`
* OS   : Ubuntu 20.04 / 22.04 (기존 news_regime 환경과 동일)
* Python : 3.1x (기존 프로젝트와 동일 버전 계열)
* 작업 디렉토리:

  * `/home/ubuntu/news_regime` 내에서 실행 (기존 CLI 스크립트와 동일 루트)
* 실행 형태:

  * (A) 단독 실행: `python -m analyst_agent` 또는 별도 스크립트
  * (B) Cron/systemd 타이머/별 scheduler 에 의해 30분마다 실행

### 2.2 사용 CLI 인터페이스 (외부 도구)

Analyst Agent는 아래 스크립트를 **외부 툴로 호출**해야 한다.

1. `run_crawler.sh` (선택적으로 사용)

   * 역할: Naver 뉴스 크롤링 + 분석 + DB 저장(기존 파이프라인)
   * 사용 시나리오:

     * 옵션으로 “분석 전에 최신 데이터 보장”이 필요할 때만 실행 (rate-limit/부하 고려)
     * 기본 모드는 기존 스케줄러/cron에 맡기고, Agent는 DB만 읽어도 됨.

2. `query_db.sh`

   * 핵심 인터페이스. Analyst Agent는 이 스크립트에 대해 다음 서브커맨드를 사용할 수 있음:

     * `./query_db.sh all --hours H --limit N`

       * 뉴스/분석/심볼매핑/추천/Regime 전체 요약
       * Analyst Agent의 기본 입력으로 활용
     * (필요 시) 세부 서브커맨드 사용:

       * `./query_db.sh news --hours H --limit N`
       * `./query_db.sh analysis --hours H`
       * `./query_db.sh symbols`
       * `./query_db.sh recommendations --limit N`
       * `./query_db.sh regime --limit N`
   * `--hours`, `--limit`는 Analyst Agent가 **설정/상황에 따라 동적으로** 결정.

3. `list_news.sh` (선택적)

   * 가장 최근 뉴스 헤더 확인용.
   * 간단한 sanity check / quick news view 용도로 사용 가능.

### 2.3 출력 인터페이스

* **터미널 출력 (stdout)**:

  * 사람이 직접 확인할 수 있는 Markdown 스타일/텍스트 보고서.
* **파일 출력**:

  * 예: `/home/ubuntu/news_regime/reports/analyst_agent_YYYYMMDD_HHMM.txt`
    또는 `.md` / `.json` 병행 저장.
* (선택) **추후 확장**:

  * DB 테이블에 저장, REST API 응답 등은 다음 단계 설계에서 옵션으로 고려.

## 3. 데이터 플로우 & 동작 시나리오

### 3.1 기본 주기 동작 시나리오 (30분 단위)

1. **스케줄 트리거**

   * 외부 scheduler (cron/systemd 등) 또는 내부 loop에 의해 Analyst Agent 프로세스 시작.
   * 주기: 기본 30분 (설정 파일/환경변수로 조정 가능).

2. **(선택) 크롤러 실행**

   * 설정에 따라:

     * `run_crawler.sh`를 호출하여 최신 뉴스/분석을 DB에 갱신.
     * 또는 스킵하고 **이미 수집된 지난 24h 데이터를 기반으로만** 분석.

3. **DB 조회 (query_db.sh 호출)**

   * 기본 호출:

     * `./query_db.sh all --hours H --limit N`

       * H: 기본 24시간 (설정 가능, 예: 12~72시간)
       * N: 기본 50~100 건(설정 가능)
   * 실패 시 재시도/에러 로그 기록.

4. **CLI 결과 파싱**

   * `all` 모드 출력에서 각 섹션별로 파싱:

     * `News Articles` 목록
     * `Article Analysis` 통계 (평균 sentiment, risk flags 등)
     * `Symbol Mappings` (심리 집중 종목)
     * `Recent Recommendations` (종목 추천)
     * `Regime History` (시간순 Regime + confidence + 설명)
   * 파싱 오류 시:

     * 해당 섹션만 graceful degrade (예: 뉴스 리스트만 보여주고 통계는 생략).

5. **분석 로직 실행**

   * Regime 변화 감지
   * 변동성/리스크 레이더 판단
   * 추천 종목과 Regime의 정합성 평가
   * 뉴스/심리 집중 종목 도출
   * 대표 뉴스 드라이버 추출

6. **리포트 생성**

   * 앞에서 정의한 **표준 출력 형식** (Regime Alert → Market Overview → Volatility → Recommendations 등)을 사용해

     * 텍스트/Markdown 리포트 생성.
   * stdout 출력 + 파일 저장.

7. **종료**

   * 프로세스 정상 종료.
   * 다음 30분 스케줄까지 대기 (scheduler에 따라).

## 4. 기능 요구사항 (Functional Requirements)

### 4.1 스케줄링 & 실행 제어

1. **주기 설정 가능**

   * `ANALYST_INTERVAL_MINUTES` 환경변수, 또는 설정 파일로 주기 변경 가능.
   * 기본값: 30분.

2. **단일 실행 모드 지원**

   * 디버깅용:

     * `python -m analyst_agent --once`
       → 크롤(optional) + 분석 + 리포트 생성 후 종료.

3. **중복 실행 방지**

   * 이전 실행이 아직 끝나지 않았을 때 새 실행이 시작되지 않도록:

     * lock 파일 / PID 체크 등으로 “동시에 두 개” 수행 방지.

---

### 4.2 CLI 호출 & 에러 처리

1. **CLI 호출 추상화**

   * `run_crawler.sh`, `query_db.sh`, `list_news.sh`를 감싸는 Python 래퍼 모듈 필요:

     * 명령어, 인자, timeout, return code, stdout/stderr 캡처.

2. **Timeout & 재시도**

   * `query_db.sh all …` 호출에 대해:

     * 일정 timeout (예: 30초) 이후 실패 처리.
     * 1~2회 재시도 후 실패시 “이번 사이클: 데이터 부족” 리포트.

3. **에러 리포트**

   * 리포트 상단에:

     * “이번 주기에는 query_db.sh에서 오류가 발생하여 최근 Regime 변화만 부분적으로 제공”
       같은 설명을 포함할 수 있어야 함.

---

### 4.3 파싱 & 내부 데이터 모델

1. **섹션 구분 파서**

   * `query_db.sh all` 출력 내 구분 라인/헤더를 기준으로:

     * News / Article Analysis / Symbol Mappings / Recommendations / Regime History
       각 섹션 텍스트를 분리.

2. **Regime History 파싱**

   * 각 Regime 항목에서:

     * timestamp, label (risk_on/sideways/…), confidence(%), 설명 텍스트 추출.
   * 시간순 정렬 및 최근 Regime 변화 감지에 사용.

3. **Article Analysis 파싱**

   * 통계 블록:

     * Total Articles, Average Sentiment, Average Impact,
     * 각 Risk Flags 카운트.
   * 필요한 경우 Top N by Impact 리스트도 파싱 가능.

4. **Symbol Mappings 파싱**

   * 종목코드별:

     * 기사 수, 평균 점수 등 추출.
   * “심리/뉴스 집중 종목” 도출에 사용.

5. **Recent Recommendations 파싱**

   * 각 추천 항목:

     * symbol, status, created_at, sentiment, impact, composite, risks dict, reason 텍스트.

6. **News Articles 파싱 (헤더 수준)**

   * 제목, Publisher, Category, Crawled, URL, Summary 라인 파싱.
   * 대표 뉴스 드라이버 추출에 사용.

---

### 4.4 Regime & 변동성 판단 로직

1. **현재 Regime 결정**

   * Regime History 중 최신 항목을 “현재 Regime”으로 사용.

2. **Regime 변화 감지**

   * 최근 K개(예: 3개) Regime 기록 비교:

     * 직전과 다른 label이 발생하면 “Regime Change”로 간주.
     * 예: risk_on → sideways, sideways → risk_off 등.
   * 변화 시점(timestamp), 이전/현재 Regime, confidence 기록.

3. **변동성 신호(Volatility Signal) 판단**

   * 다음 요소들을 조합:

     * Regime 변화 유무 및 방향 (risk_on→sideways vs sideways→risk_off 등)
     * Article Analysis의 평균 Impact 수준
     * 특정 리스크(예: Regulation, Earnings)가 급증했는지 (flag count 비교)
   * 결과:

     * NORMAL / WATCH / CAUTION / SPIKE 등 3~4단계 상태로 요약.

4. **사용자 친화적인 요약문 생성**

   * Regime 변화/변동성 상태를:

     * “상승 모멘텀에서 중립으로 완화”,
       “중립에서 위험회피 구간으로 전환” 등 자연어로 표현.

---

### 4.5 추천 종목·심리 집중 종목 분석

1. **추천 종목 요약**

   * `Recent Recommendations` 파싱 결과로:

     * 상위 N개 종목(기본 5개) 선택.
     * 각 종목별 Sentiment/Impact/Composite와 Reason 텍스트 구조화.

2. **Regime-종목 정합성 평가 (룰 기반)**

   * 예시:

     * 현재 Regime이 risk_on → 성장/모멘텀 종목 추천에 우호.
     * sideways → 안정/대형주 위주 또는 개별 모멘텀.
     * risk_off → 방어주/현금비중 확대 등 정보성 코멘트.
   * 종목의 특성을 DB/심볼정보/뉴스 키워드로 유추해,
     “현재 시장 분위기와 어떤 관계인지”를 텍스트로 표현.

3. **심리 집중 종목 도출**

   * `Symbol Mappings`에서 기사 수 상위 종목 및 평균 sentiment가 높은 종목을 뽑아:

     * “뉴스와 심리가 몰려 있는 종목”으로 리포트에 표시.

---

### 4.6 리포트 생성 & 저장

1. **출력 포맷 표준화**

   * 이전에 정의한 템플릿을 기준으로:

     * [Regime Alert]
     * [Market Overview]
     * [Volatility & Risk Radar]
     * [Top Recommendations]
     * [Focus Symbols]
     * [Key News Drivers]
     * [Summary & Checkpoints]
   * 섹션별 헤더/항목 이름은 고정 또는 설정으로 관리.

2. **텍스트/Markdown 출력**

   * stdout에 그대로 출력 (터미널 확인용).
   * 동일 내용을 파일로 저장.

3. **파일 저장 규칙**

   * 디렉토리: `/home/ubuntu/news_regime/reports/`
   * 파일명 예:

     * `analyst_report_20251203_1336_sideways.txt`
   * 파일명에 timestamp + current regime 포함 (grep/search 용이).

## 5. 비기능 요구사항 (Non-functional)

1. **성능**

   * 30분마다 실행 기준:

     * 각 사이클의 전체 실행 시간(크롤 + query_db + 분석 + 리포트)은 수 초~수십 초 내.
   * 크롤러 실행 옵션을 켜더라도 전체 사이클이 30분 내 충분히 완료되도록 설계.

2. **신뢰성 & 복원력**

   * query 실패/파싱 실패 시에도:

     * 기존 Regime History 일부 사용, 혹은 “이번 사이클 데이터 부족” 메시지로 degrade.
   * 예외 발생 시:

     * 로그 기록 + 리포트에 요약된 에러 정보 포함.

3. **확장성**

   * `query_db.sh` 출력 포맷이 일부 확장되더라도:

     * 섹션별 파서를 느슨하게 설계하여 필수 필드만 사용.
   * 향후:

     * KIS/OpenAPI 가격 데이터와 결합해 “뉴스 이후 수익률/성과 분석” 확장 가능.

4. **로깅 & 모니터링**

   * Agent 실행 시작/종료, 각 CLI 호출 결과, 에러/타임아웃 등의 로그를 남김.
   * 최소한:

     * `/home/ubuntu/news_regime/logs/analyst_agent.log` 등.

5. **구성 관리**

   * 주기/시간창/limit/리포트 디렉토리/Regime 변화 민감도 등은:

     * YAML/JSON 설정 파일 또는 환경변수로 관리.

## 6. 가정 & 제약

* `/home/ubuntu/news_regime` 내 CLI (`run_crawler.sh`, `query_db.sh`, `list_news.sh`)는 이미 검증되어 있고,
  특정 포맷으로 출력한다는 것을 전제로 한다.
* Analyst Agent는 **DB 쓰기/스키마 변경을 하지 않는다** — 오로지 읽기 + 리포트 생성.
* 투자 판단은 사용자의 몫이며, Agent는 **정보 요약/분석 도구**임을 계속 유지해야 한다.
